# JAYRA / MYRAA Feature and Integration Inventory

This inventory records user-visible features, backend capabilities, support modules, and standalone/experimental entry points found in the repository. Status reflects source wiring, not whether an external API key, permission, device, model, or packaged build is available at runtime.

- **[Connected & Active]** means code is mounted, imported, registered, called by the server/runtime, or otherwise reachable through an active application path.
- **[Orphaned / Unlinked / Needs Wiring]** means source exists but no active route/render/call path was found. Standalone previews and test-only code are identified separately.

There is no root-level `components/` directory; React components live in [`src/components/`](./src/components/).

## 4. Source-to-Runtime Wiring Summary

1. Electron starts the local Node server and optionally the packaged Python sidecar; the renderer loads through the local server origin.
2. The React app mounts behind key/crash gates, obtains canonical settings through the backend API, and consumes runtime events.
3. Live audio/text enters the Gemini session. Direct tools use backend handlers; multi-step or screen-dependent work is handed to the bounded task manager.
4. Desktop, telemetry, screen, task, and conversation events enter the runtime/cognition systems. Proactive speech is generated by the model only after cadence, presence, DND, cognition and safety gates allow it.
5. Screen pixels use explicit capture/inspection paths; foreground-window metadata polling is separate and does not imply continuous screenshot sharing.
6. Python desktop tools and Android phone commands connect through local authenticated service/socket paths; capability permissions and confirmations gate consequential actions.
7. Results, transcripts, telemetry, tasks, confirmations, diagnostics and summaries flow back to the HUD or connected phone client.

## 5. Plugin Package and Trust Configuration

The plugin manager stores packages under `<application-data>/plugins`; the Python sidecar stores validated tool modules under `<application-data>/plugins/python_tools`. Packaged Electron builds pass Electron's writable `userData` directory to the backend. Source development uses the configured `JAYRA_DATA_DIR`/`MYRAA_DATA_DIR`, or the existing local `.myraa-data` fallback. The installation directory is never used for downloaded plugin writes.

Remote synchronization is disabled unless both `JAYRA_PLUGIN_UPDATE_URL` and `JAYRA_PLUGIN_PUBLIC_KEY` are configured. The public key must be Ed25519 PEM or base64-encoded DER/SPKI. The URL may return a signed package JSON directly, or a GitHub Releases API response containing a `.jayra-plugin.json` asset. A configured source is checked at startup and then every six hours; `/api/brain/plugins/sync` triggers an on-demand check.

A signed package contains exactly `manifest`, `files`, and base64 `signature`. The Ed25519 signature covers UTF-8 canonical JSON of `{manifest, files}` (recursively sorted object keys; `files` sorted by path). The manifest requires `schemaVersion: 1`, a slug `id`, semantic `version`, metadata, and one or more tool descriptors. Tool names must be prefixed with the plugin ID normalized to underscores (for example `demo-plugin_echo` becomes `demo_plugin_echo`), each entry point must be a `tools/*.py` file, and the only currently supported requested capability is `code_execution`. Files are limited to safe relative paths and a 5 MB total package size.

Python tool entries are not imported directly by the Node server: the package is passed to the desktop sidecar's source/schema validator and hot-loader. Tool execution still uses the Central Brain's permission checks and high-risk confirmation policy. Invalid signatures, manifests, paths, Python tool sources, or failed activations are rejected, diagnosed, and isolated; partial activation is rolled back where possible.
